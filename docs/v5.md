# LeekScript v5 — Spécification, design et roadmap

> Document vivant de la branche `v5`. Décrit **le langage** (syntaxe, sémantique,
> exemples), **le design d'implémentation** (effacement, gates, codegen) et
> **l'état d'avancement**.

LeekScript v5 fait évoluer le langage sur trois piliers — **génériques**,
**bibliothèque standard objet**, **modules** — sans casser la sémantique des
versions 1 à 4. Toute nouvelle sémantique est gardée derrière `version >= 5`.

- `LATEST_VERSION = 5` (les IA choisissent leur version via `@version: 5`).
- Le comportement v1–v4 est **gelé** : aucun changement observable en deçà de v5.

---

## 0. Principe de compatibilité

Le comportement v1–v4 est gelé. Les ~100 points de bascule existants
(`getVersion() >= 2/3/4`) forment le contrat de compatibilité ; v5 est *additif*
à ces endroits, sauf breaking change explicitement décidé et documenté ici.

Plutôt que de semer des `>= 5` magiques dans tout le compilateur, les bascules v5
passent par un point unique :

```
leekscript/common/LanguageFeature.java
  enum LanguageFeature { GENERICS(5), OO_STDLIB(5), ... ;
                         final int since; boolean enabledIn(int v) }
```

On **ne réécrit pas** les 100 gates d'un coup : on route les nouveaux gates v5
par `LanguageFeature`, et on migre l'existant opportunément.

### Stratégie de dépréciation

Pour les formes supprimées en v5, deux régimes selon le risque de migration :

- **Erreur dure** quand la forme méthode/namespace est un remplacement direct et
  mécanique (cas des fonctions de collection, voir §2.2).
- **Warning de dépréciation** (palier avant suppression) pour les formes très
  répandues dont la migration des IA joueurs n'est pas encore outillée (cas des
  fonctions mathématiques libres, voir §2.4). Suppression dure dans une v5.x
  ultérieure une fois la télémétrie au vert.

## 1. Génériques

Les génériques sont **purement compile-time** : on compile vers Java en
**effaçant** les types (le runtime LeekScript reste dynamique). Aucune
modification du runtime (`runner/values/*`) n'est nécessaire — énorme réduction
de risque, pas de monomorphisation.

### 1.1 Fonctions utilisateur génériques ✅

Les paramètres de type se déclarent **après le nom** de la fonction (la syntaxe
`function<…>` est déjà réservée au type `Function<…>` côté expression).

```leekscript
function first<T>(Array<T> list) -> T {
    return list[0]
}

integer x = first([1, 2, 3])      // T = integer, x : integer
string  s = first(["a", "b"])     // T = string,  s : string
```

**Implémentation.** `T` est résolu en `TypeVariable` pendant le parse des types
(portée = chaîne des `FunctionBlock` englobants, `WordCompiler.findTypeParameter`).
À l'appel (`LeekFunctionCall.verifyVersions`) : inférence structurelle
(`inferTypeVariables` param formel ↔ arg effectif) → `substitute` dans le type de
retour, réutilisant la résolution par distance de cast existante. No-op pour les
versions non génériques (zéro impact existant). Une variable non liée s'efface
vers sa borne (`any`) ; le retour effacé `Object` est re-casté au site d'appel.

### 1.2 Signatures système génériques ✅

Les fonctions de la bibliothèque qui le justifient sont désormais typées
précisément au lieu de retourner `any` :

```leekscript
Array<integer> a = [3, 1, 4, 1, 5]
integer m = a.max()                       // -> integer, pas any
Array<integer> b = a.map(x -> x * 2)      // map<T,R> : Array<R>
```

**Implémentation.** Les `CallableVersion` portent des `TypeVariable`. Inférence
**contravariante** : une variable n'est inférée que depuis le *retour* d'un
callback, jamais ses paramètres (sinon le `any` d'un lambda non typé polluerait
`T`). Les params de callback de la stdlib restent `any` (LeekScript ne type pas
contextuellement les lambdas).

### 1.3 Classes génériques ✅

La déclaration, la portée des paramètres de type, l'effacement **et le typage précis
à l'instanciation** fonctionnent :

```leekscript
class Box<T> {
    T value
    constructor(T v) { value = v }
    T get() { return value }
}

var b = new Box(5)     // inféré Box<integer> depuis l'argument du constructeur
integer i = b.get()    // -> integer (plus `any`) ; assigner à un string warn en strict
```

**Implémentation.** Déclaration : interface partagée `TypeParameterScope` (implémentée
par `FunctionBlock` et `ClassDeclarationInstruction`) ; `T` se résout dans les types
des champs/méthodes/constructeur.

Instanciation précise : `ParameterizedClassType` (= `ClassType` + `Map<TypeVariable,
Type>` de liaisons). À `new Box(5)` (branche `VariableType.CLASS` de `LeekFunctionCall`),
on infère les liaisons depuis les **arguments du constructeur** avec le même
`inferTypeVariables` que les fonctions ; les variables non liées s'effacent vers `any`.
`member()`/`elementAccess()` substituent les liaisons, donc `b.value` (champ) comme
`b.get()` (méthode) se lisent précisément. Pas de syntaxe explicite `new Box<integer>(…)`.
Variance **invariante** (`Box<integer>` ≠ `Box<string>`), un `ClassType` brut reste
assignable des deux côtés (permissif par effacement). Codegen **inchangé** (mêmes noms
`u_<Class>`, classe Java non générique) ; seule subtilité : la méthode/le champ effacés
renvoient `Object` en Java, donc on insère un cast `(Wrapper)` au site d'accès quand le
type inféré est concret (sinon `ops((Object)…)` affecté à un primitif casse au javac).

### Variance

Démarrer **invariant** partout (sûr, = comportement actuel d'`ArrayType.accepts`).
Ajouter la covariance en position lecture seule plus tard.

## 2. Bibliothèque standard objet

Objectif : « plus de fonctions qui traînent seules ». La stdlib devient objet :
des **méthodes** sur les valeurs et des **namespaces** pour les fonctions
statiques/utilitaires.

Chaque fonction de `LeekFunctions` porte déjà un `standardClass` (`"Number"`,
`"String"`, `"Array"`, `"JSON"`…) et un flag `isStatic` — c'est la source qui
alimente les deux formes ci-dessous. Deux formes de codegen coexistent :
statique (`NumberClass.sqrt(ai, x)`) et instance (`((ArrayLeekValue) a).sort(ai)`).

### 2.1 Méthodes sur les valeurs ✅

`valeur.méthode(args)` sur les types natifs Array, Map, Set, String, Number :

```leekscript
var a = [3, 1, 2]
a.sort()                       // mutation en place
a.push(4)
var n = a.count()              // 4
var d = [1, 2, 3].map(x -> x * 2)   // [2, 4, 6]

var s = "Hello"
s.length()                     // 5
s.toUpper()                    // "HELLO"
s.substring(1, 3)              // "ell"

var x = -5
x.abs()                        // 5
(9.0).sqrt()                   // 3.0  (receveur typé/var, pas littéral)
```

**Implémentation.** `standardClassOf(Type)` / `methodFor(Type, name)` côté
compilo ; codegen branche sur `isStatic()` (instance `((ArrayLeekValue) x).m(ai)`
vs statique `StringClass.m(ai, recv, args)`). Pour un receveur de type statique
`any` (`var x = …`, très courant), résolution **runtime** dans
`AI.callObjectAccess` (gardée v≥5). Les noms sont propres : `LeekFunctions.javaName`
découple le nom leekscript du nom Java (`map` → `arrayMap`), `alias()` enregistre
un alias method-only. Marche sur receveur typé, `var` et littéral.

### 2.2 Suppression des formes libres Array/Map/Set/String ✅

En **v5**, les fonctions de collection ne sont plus appelables en forme libre :
**erreur dure** qui pointe vers la forme méthode.

```leekscript
// v5
var a = [3, 1, 2]
sort(a)        // ❌ erreur : utilise a.sort()
a.sort()       // ✅
push(a, 4)     // ❌ erreur : utilise a.push()
a.push(4)      // ✅
```

**Implémentation.** Une boucle abaisse `maxVersion=4` pour les ~100 fonctions
Array/Map/Set/String et pose un `replacement` = nom de méthode propre. v1–v4
inchangés. Les fonctions **math** de Number sont aussi retirées en v5 (voir §2.4) ;
les utilitaires bit/entier de Number, et Value/JSON/System/Color, restent libres.

### 2.3 Namespaces ✅

Les fonctions statiques/utilitaires sont regroupées dans des **namespaces**.
`Namespace.func(args)` se résout et se génère **exactement** comme l'ancienne
forme libre `func(args)`, juste qualifié et gardé v≥5.

```leekscript
// Mathématiques — résout aussi rand/randInt (pas de receveur de valeur)
Math.sqrt(16)          // 4.0
Math.abs(-5)           // 5
Math.pow(2, 10)        // 1024.0
Math.max(3, 7)         // 7
Math.rand()            // réel dans [0, 1)
Math.randInt(0, 10)

// JSON (noms propres : jsonEncode -> JSON.encode)
JSON.encode([1, 2, 3]) // "[1,2,3]"
JSON.decode("[1,2,3]") // [1, 2, 3]

// String (helpers statiques)
String.charAt("hello", 1)     // "e"
String.split("a,b,c", ",")    // ["a", "b", "c"]

// Array / Map / Set — la forme namespace reste valide même si la forme libre
// est retirée en v5
Array.sort(a)
Array.map([1, 2, 3], x -> x * 2)
Map.size(m)
Set.contains(s, 2)

// Number (équivalent de Math), System
Number.sqrt(9.0)       // 3.0
System.debug(x)
```

Namespaces exposés : **Math, Number, String, Array, Map, Set, JSON, System**.

**Implémentation.** Chaque namespace est une classe interne (comme `JSON`/`System`,
`Math` ajouté gardé v≥5) ; `LeekFunctions.namespaceFunction(ns, field)` mappe le
nom de namespace vers sa classe standard (`Math` → `Number`, les autres par
identité). Le codegen du callee système est factorisé (`writeSystemFunctionCallee`)
et **partagé** entre forme libre et forme namespace. Trois points :

1. La suppression `maxVersion=4` (§2.2) ne s'applique **pas** aux appels
   namespace : `sort(a)` est une erreur en v5, mais `Array.sort(a)` reste valide
   (garde `!is_namespace_function` dans `verifySystemFunction`).
2. Le codegen utilise `getJavaName()` (pas `getName()`) pour les fonctions
   aliasées (`JSON.encode` → `jsonEncode`, `Array.map` → `arrayMap`) ; identique
   sans alias, donc zéro impact sur les formes libres existantes.
3. `Color` n'est pas exposé : aucune classe interne `Color` n'est enregistrée.

### 2.4 Politique « plus de fonctions qui traînent »

| Catégorie | Forme libre en v5 | Forme canonique v5 |
|-----------|-------------------|--------------------|
| Collections (Array/Map/Set/String) | ❌ erreur dure | `a.sort()` ou `Array.sort(a)` |
| Mathématiques (sqrt, abs, cos, min, max, pow…) | ❌ erreur dure | `Math.sqrt(x)` |
| Bit/entier (binString, bitLength, hexString…) | tolérée | (reste libre, pas des maths) |
| JSON, System | tolérée | `JSON.encode(v)`, `System.debug(x)` |
| Fonctions métier (`getCell`…) | hors périmètre du cœur | traité côté générateur |

Les fonctions **métier** du générateur (injectées via `extraFunctions`) sont hors
périmètre du cœur leekscript ; leur regroupement objet sera traité séparément.

**Constantes de namespace ✅** : `Math.PI`, `Math.E`, `Math.Infinity` (accès de champ,
pendant v5 des constantes libres ; champs `final` non assignables). Comme pour les
fonctions, il faut les deux côtés : compile-time dans `MainLeekBlock` (typage, gardé
v≥5) ET runtime dans `AI` (`mathClass.addStaticField`, sinon le `getField(mathClass…)`
généré ne résout pas). `NaN` non exposé (non représentable en littéral Java). Les
constantes entières/réelles restent sur `Integer`/`Real` (`Integer.MAX_VALUE`…).

**Suppression des formes libres math ✅** : en v5, `sqrt(x)`/`abs(x)`/`cos(x)`/`min`/`max`/
`pow`/`floor`/`rand`… sont une **erreur dure** (REMOVED_FUNCTION_REPLACEMENT) pointant vers
`Math.sqrt(x)`. Même mécanique que les collections (§2.2) : une liste EXPLICITE de noms math
(pas tout `standardClass=Number`, qui contient aussi des utilitaires bit/entier `binString`/
`bitLength`/`hexString`/`isNaN`… qui RESTENT libres) passe `maxVersion=4` + `replacement="Math."+nom`.
La forme `Math.f(x)` reste valide (gardée `!is_namespace_function`). Migration : ~270 assertions
de test cappées à v4 (la forme libre reste testée v1-4 ; le v5 l'est via les ~20 tests `Math.*`).

## 3. Modules ✅

Remplacer le `include()` à fusion plate par de vrais modules (un fichier = un
module, symboles privés par défaut).

```leekscript
// utils.leek
export function clamp(x, lo, hi) { ... }
export class Vec { ... }
function helper() { ... }            // non exporté = privé au module

// main.leek
import { clamp, Vec } from "utils"
import * as Geo from "geometry"
```

**Implémentation prévue.** `ModuleScope` entre le scope global et le fichier,
tables de symboles **par module** au lieu de la fusion unique ; codegen à une
seule classe Java mais noms qualifiés par module (`module$utils$clamp`). Réutilise
le DAG `IncludeGraph` existant (cycles gérés par le double-pass). `include()` est
**supprimé en v5** (erreur `INCLUDE_REMOVED_IN_V5`) : il reste réservé à v≤4.

Découpage : 3a. parse `export`/`import … from` · 3b. `ModuleScope` + résolution
qualifiée + codegen renommé · 3c. `import * as Ns`.

**3a ✅ FAIT** : `MODULES(5)` dans `LanguageFeature` ; `export <decl>` et
`import { a, b } from "file"` parsent en v5 (firstPass + secondPass de WordCompiler,
helper `importStatement()`), erreur dure `KEYWORD_UNEXPECTED` avant v5. SYNTAXE SEULE :
`export` est consommé (la déclaration marche normalement), `import` parse sans résoudre
ni lier — le scoping privé-par-défaut, la résolution de module et le codegen qualifié
sont la phase 3b. Tests `TestModules`.

**3b (fonctions) ✅ FAIT** : `import { f } from "file"` résout et lie réellement.
Un fichier importé devient un `Module` (classe `compiler/bloc/Module`) avec ses
symboles **privés par défaut** — seules les fonctions `export`ées sont importables
(sinon `SYMBOL_NOT_EXPORTED`). L'entrypoint est le *module principal* (préfixe de
codegen vide → **v1–v4 byte-identique**, y compris les `include()` de v≤4 qui y
fusionnent à plat) ; les modules importés
reçoivent un préfixe collision-proof `$m<id>$` (le `$` n'est pas un caractère
d'identifiant LeekScript), porté par `FunctionBlock.getInternalName()`. Mécanique :
`MainLeekBlock` est le registre des modules + sink codegen unique (réutilise la machine
`include` : `importModuleFirstPass`/`importModule` miroirs de `includeAIFirstPass`/
`includeAI`) ; résolution module-aware via `getUserFunction(name, module)` (imports
puis fonctions propres préfixées, pas de fallback global pour un module importé =
privacy) ; le `FunctionBlock` résolu est caché sur le `LeekVariable` (preAnalyze)
pour que le codegen émette le bon nom préfixé. Les fonctions d'un module importé NE
sont PAS déclarées comme variables du bloc partagé (sinon collision/pollution) ;
le corps d'une fonction se résout dans le module qui la déclare (save/restore du
module dans `FunctionBlock.preAnalyze`/`analyze`). Tests `TestModulesResolution`
(harness filesystem).

**Variables/globales ✅** : au niveau module, `var x` reste un local per-tour (idiome
LW, invisible aux fonctions) ; `export var x` = champ module **ré-initialisé chaque
tour** ; `global x` = champ **persistant** (combat) ; `export global x` = persistant +
importable. Même mécanique de préfixe (`g_$m<id>$<name>`) + registre module-aware
(`getGlobal(name, module)`). `var` nu reste un local (sinon casse session/REPL + coût
en ops).

**Classes ✅** : `export class` / import — `new C()`, méthodes, héritage, accès statique,
préfixe `u_$m<id>$<Class>`. Les instances étant typées dynamiquement (`ClassLeekValue`),
le préfixe ne touche que la def + les références. Résolution `getDefinedClass(name,
module)` (les classes internes Array/Map restent visibles partout).

**3c `import * as Ns` ✅** : `import * as Geo from "geo"` aliase le module ;
`Geo.membre` résout fonction (`f_…(args)`), variable (`g_…`) ou classe
(`new Geo.Vec()` → `new_u_…`) dans le module aliasé, avec check exporté.
`VariableType.MODULE_NAMESPACE` + `Module.namespaceImports`.

**Pilier 3 COMPLET.** `include()` est retiré en v5 (erreur `INCLUDE_REMOVED_IN_V5`).

### Expression `match` ✅ (#2404)

`switch` (instruction, depuis v3) reste inchangé. En v5 s'ajoute `match`, une
**expression** de filtrage par valeur qui renvoie une valeur :

```leekscript
var label = match (note) {
    0, 1, 2 -> "faible",
    3       -> "moyen",
    _       -> "élevé"
}
```

Motifs v1 : littéraux (comparés via `eq`), plusieurs valeurs par branche (`a, b ->`),
joker `_` (cas par défaut, fallback final quelle que soit sa position). Sans branche
correspondante ni `_`, le match vaut `null`. Type du résultat = `any` (affinage de
type, motifs de type `is T` et gardes `if` = évolutions ultérieures).

Mécanique : désugaré en chaîne de ternaires ; le **sujet est évalué une seule fois**
(assigné à un champ `__match_<id>` dans la première comparaison, relu ensuite). Gardé
`LanguageFeature.MATCH` ; en v1-4 `match` reste un identifiant ordinaire (byte-identique).
Limitation : un sujet à effets de bord dans un match sans aucune branche de valeur
(seulement `_`) n'est pas évalué.

### Sucre syntaxique — boucle `for` implicite ✅ (#358)

En v5, `for <collection> { ... }` itère la collection avec une variable de boucle
implicite nommée `it` (désugaré en `foreach`) :

```leekscript
var s = 0
for [1, 2, 3] { s += it }   // s == 6
```

`it` reste un identifiant ordinaire en dehors de la boucle (pas réservé). Gardé
`LanguageFeature.FOR_IMPLICIT_IT` : en v1-4 `for <expr>` exige toujours une
parenthèse ouvrante (byte-identique). Limitation v1 : deux boucles implicites
imbriquées entrent en collision sur `it` (utiliser `for (x in ...)` pour imbriquer).

Chaque phase = **compilable + testée + non régressive** sur la suite v1–v4.

### Phase 6 — inférence du type de retour, tranches 1+2 ✅ (#43)

Une fonction non annotée infère son type de retour = **union des types de ses `return`**
(+ `null` si le corps peut tomber en fin), au lieu de `any`. Les appelants reçoivent un
type précis → moins de dispatch dynamique. Gardé v5 (`RETURN_TYPE_INFERENCE`) ; v1-4
inchangé. La récursion retombe sur `any` (pas de point fixe). **Tranche 2** : analyse
**paresseuse à la demande** (un appelant déclenche l'analyse de l'appelé, analyze rendu
idempotent) → propagation déterministe à travers les chaînes de helpers quel que soit
l'ordre de déclaration. Design complet et invariants :
[`docs/v5-inference-design.md`](v5-inference-design.md).

### Phase 6 — inférence des types de PARAMÈTRES par monomorphisation, 1ʳᵉ tranche ✅ (#43 T3)

Un paramètre non annoté appelé avec un type concret (int/real/bool/string, une classe
utilisateur, une classe générique instanciée `Box<integer>`, ou Array/Map/Set) crée une
**variante spécialisée** de la fonction : son corps est **re-parsé** dans un bloc frais aux paramètres
typés, analysé **une seule fois** (pas de ré-analyse → pas de problème d'idempotence), et
émis comme méthode Java `f_<nom>$<profil>(<params typés>)`. Chaque site d'appel **dispatche
statiquement** vers la variante de son profil ; le type de retour précis de la variante
**se propage à l'appelant** (`integer m = dbl(5)` ne warn plus en strict v5). Création **à la
demande** pendant l'analyse (style T2), avec cache (récursion), abandon silencieux si la
spécialisation invalide le corps (→ générique), gardé v5 (`PARAMETER_TYPE_INFERENCE`) ; v1-4
byte-identique. Profils supportés : **int/real/bool, string, classes utilisateur, classes
génériques instanciées (`Box<integer>`) et Array/Map/Set** (le `getHP(entity)` de l'issue,
avec dispatch virtuel préservé). Pour une classe générique la spécialisation est SÛRE (la
classe s'efface vers un seul code Java quel que soit T, sans overload système value-changing
comme `Array.sum()`) : le typage précis n'affine que les membres (`b.value` : `T`→`int`) via
la machinerie Phase 2 ; la clé de cache inclut les liaisons (`Box<int>`/`Box<string>` =
variantes distinctes). Paramètres par défaut tolérés (seuls les appels passant tous les
arguments monomorphisent) ; fonctions des modules importés incluses (re-parse depuis le flux
du module). **Exclus** : paramètres `@référence` (boxés, sémantique de référence + valeur
marginale), fonctions génériques (`function f<T>`) et type guards. Détails et limites :
[`docs/v5-inference-design.md`](v5-inference-design.md) §Tranche 3.

> ⚠️ Tentative antérieure par **ré-analyse** (2 passes : collecte → seed → ré-analyse
> autoritaire) abandonnée : `analyze` n'est pas rejouable (compteur d'ops `ConditionalBloc`
> + narrowing de champs s'accumulent). La monomorphisation contourne en analysant chaque
> variante 1× sur un AST frais.

### Phase 6 — type guards ✅ (#42)

Une fonction peut déclarer un **prédicat de type** sur l'un de ses paramètres : quand
l'appel sert de condition, l'argument correspondant est affiné dans la branche vraie
(et, si son type est un compound, réduit dans la branche fausse), comme un `instanceof`.

```leekscript
function isString(any x) -> x is string {
    return typeOf(x) == TYPE_STRING
}

string | integer v = "hello"
if (isString(v)) {
    return v.length()      // v affiné en `string` ici
}
return v + 1               // v affiné en `integer` ici (branche fausse)
```

La syntaxe réutilise la position du type de retour (`-> param is Type`) ; la fonction
renvoie un `boolean`. Gardé v5 (`LanguageFeature.TYPE_GUARDS`).

**Implémentation** : au parse (`WordCompiler`, après `->`), `param is Type` est reconnu,
l'index du paramètre est résolu (`TYPE_GUARD_PARAMETER_UNKNOWN` si le nom n'est pas un
paramètre), le prédicat est stocké sur le `FunctionBlock` et le type de retour fixé à
`boolean`. `NarrowingInfo.extractInto` ajoute un cas : quand la condition est un appel à
une fonction porteuse d'un guard, l'argument à l'index gardé (s'il s'agit d'une variable)
est affiné. S'intègre gratuitement avec `!`, `&&`, `||` (qui recursent via `extract`).

**Méthodes de classe** : un type guard peut aussi être porté par une méthode (d'instance
ou statique) : `public isB(any x) -> x is B { ... }`. Comme le type de retour des méthodes
est en préfixe, `-> param is Type` après les paramètres est réservé au seul prédicat
(gated v5 ; sinon l'ARROW n'est pas consommée et le parse reste byte-identique). Le guard
est stocké sur `ClassMethodBlock` (mêmes accesseurs que `FunctionBlock`, remontés sur
`AbstractLeekBlock` avec un défaut « pas de guard »). `LeekFunctionCall` mémorise la méthode
résolue (`resolvedMethod`, posée sur les trois chemins `this.m()` / `m()` / `Class.m()`) ;
`NarrowingInfo` affine via le callable résolu commun `getResolvedCallable()`. L'appel sur un
récepteur typé / `this` / non qualifié est affiné ; un récepteur de type statique `any` ne
l'est pas (la méthode n'est pas résolue statiquement).

**Argument = accès de champ** : l'argument du guard peut être une variable simple OU un
accès de champ (`if (isB(this.field))` / `if (isB(obj.field))`), auquel cas c'est la
propriété qui est affinée (même chemin que le cas property de `instanceof`). Corrige au
passage une asymétrie codegen pré-existante : `this.field` affiné insère désormais le cast
au site de lecture (`((B) field)` pour une classe, `((String) field)` pour une string)
comme `obj.field`, donc `this.field.méthode()` compile — que la méthode soit une méthode de
classe (`this.field.m()`) ou une méthode string statique (`this.field.length()`). Bénéficie
aussi à `instanceof this.field`.

**Types paramétrés** : un guard peut viser un type paramétré non interné
(`-> x is Array<integer>`) ; la réduction de branche fausse retire bien le type du compound
(`CompoundType.removeType` compare par égalité STRUCTURELLE, plus seulement par identité —
bénéficie aussi à `instanceof`).

**Limites** : portée = fonctions libres nommées et méthodes (pas les fonctions anonymes).
Les guards portés par une **lambda** ne sont pas retenus : implémentables (guard sur le
`FunctionType`) mais UNSOUND sous réassignation (le type d'un `var` est figé à la
déclaration et le guard, ignoré par la compatibilité de types, persisterait après
réassignation à une lambda sans guard → affinage périmé). Les rendre sûrs exigerait une
variance guard-aware sur `FunctionType.accepts`, disproportionnée pour ce cas marginal.

### Phase 6 — validation `@tailrec` ✅ (#44)

L'annotation `@tailrec` vérifie qu'une fonction est bien récursive terminale : tout
appel récursif doit être en **position terminale**. Sinon, erreur dure
`ANNOTATION_TAILREC_NOT_TAIL` (code 166) pointant l'appel fautif.

```leekscript
@tailrec function sum(n, acc) {
    if (n == 0) return acc;
    return sum(n - 1, acc + n);     // ✅ position terminale
}

@tailrec function bad(n) {
    if (n == 0) return 0;
    return bad(n - 1) + 1;          // ❌ ANNOTATION_TAILREC_NOT_TAIL (imbriqué dans +)
}
```

Sont **terminaux** : l'expression directe d'un `return` non optionnel, à travers les
parenthèses (`return (f(x))`), les **deux branches** d'un ternaire
(`return c ? f(a) : f(b)`) et l'**opérande droit** d'un `&&`/`||`
(`return base || f(x)` — `f(x)` coercé en booléen est la valeur retournée quand le
court-circuit gauche ne se déclenche pas ; idiome courant des prédicats récursifs),
récursivement. Ne le sont **pas** : un appel imbriqué dans un opérateur arithmétique
(`f(n) + 1`), l'**opérande gauche** d'un `&&`/`||` (`return f(x) || c`, dont la valeur
est combinée), un appel en instruction, dans une déclaration, dans la condition d'un
ternaire, ou via `return?` (qui peut poursuivre l'exécution).

**Implémentation** (greffée sur la passe `analyze`, sans énumérer les types
d'instructions) : un appel résolu vers la fonction courante (récursion directe)
s'enregistre sur son `FunctionBlock` ; `LeekReturnInstruction.analyze` marque
récursivement les appels en position de queue (`trim()` pour les parenthèses, descente
dans les branches de ternaire et l'opérande droit de `&&`/`||`) ; `FunctionBlock.analyze`
lève l'erreur pour tout appel récursif collecté non marqué. La portée de
`getCurrentFunction()` exclut naturellement les appels logés dans une fonction anonyme
imbriquée. **Opt-in** : inactif sans l'annotation (aucune régression).

**Méthodes de classe** : `@tailrec` est aussi validé sur les méthodes (d'instance et
statiques). Même mécanique mirrorée sur `ClassMethodBlock` ; l'auto-appel direct est
reconnu sur les trois chemins de résolution (`m()` non qualifié, `this.m()`, `Class.m()`)
via `LeekFunctionCall.registerMethodSelfCall`, et `LeekReturnInstruction.markTailCalls`
marque la position terminale à travers un getter commun `getResolvedCallable()` (fonction
ou méthode courante). Un auto-appel logé dans une fonction anonyme imbriquée dans la
méthode n'est pas terminal (fonction courante = l'anonyme).

Les positions terminales couvertes (ternaire, parenthèses, opérande droit de `&&`/`||`)
valent pour les fonctions comme pour les méthodes.
