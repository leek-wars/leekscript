# LeekScript v5 — Spécification, design et roadmap

> Document vivant de la branche `v5`. Décrit **le langage** (syntaxe, sémantique,
> exemples), **le design d'implémentation** (effacement, gates, codegen) et
> **l'état d'avancement**.

LeekScript v5 fait évoluer le langage sur trois piliers — **génériques**,
**bibliothèque standard objet**, **modules** — sans casser la sémantique des
versions 1 à 4. Toute nouvelle sémantique est gardée derrière `version >= 5`.

- `LATEST_VERSION = 5` (les IA choisissent leur version via `@version: 5`).
- Le comportement v1–v4 est **gelé** : aucun changement observable en deçà de v5.

---

## 0. Principe de compatibilité

Le comportement v1–v4 est gelé. Les ~100 points de bascule existants
(`getVersion() >= 2/3/4`) forment le contrat de compatibilité ; v5 est *additif*
à ces endroits, sauf breaking change explicitement décidé et documenté ici.

Plutôt que de semer des `>= 5` magiques dans tout le compilateur, les bascules v5
passent par un point unique :

```
leekscript/common/LanguageFeature.java
  enum LanguageFeature { GENERICS(5), OO_STDLIB(5), ... ;
                         final int since; boolean enabledIn(int v) }
```

On **ne réécrit pas** les 100 gates d'un coup : on route les nouveaux gates v5
par `LanguageFeature`, et on migre l'existant opportunément.

### Stratégie de dépréciation

Pour les formes supprimées en v5, deux régimes selon le risque de migration :

- **Erreur dure** quand la forme méthode/namespace est un remplacement direct et
  mécanique (cas des fonctions de collection, voir §2.2).
- **Warning de dépréciation** (palier avant suppression) pour les formes très
  répandues dont la migration des IA joueurs n'est pas encore outillée (cas des
  fonctions mathématiques libres, voir §2.4). Suppression dure dans une v5.x
  ultérieure une fois la télémétrie au vert.

## 1. Génériques

Les génériques sont **purement compile-time** : on compile vers Java en
**effaçant** les types (le runtime LeekScript reste dynamique). Aucune
modification du runtime (`runner/values/*`) n'est nécessaire — énorme réduction
de risque, pas de monomorphisation.

### 1.1 Fonctions utilisateur génériques ✅

Les paramètres de type se déclarent **après le nom** de la fonction (la syntaxe
`function<…>` est déjà réservée au type `Function<…>` côté expression).

```leekscript
function first<T>(Array<T> list) -> T {
    return list[0]
}

integer x = first([1, 2, 3])      // T = integer, x : integer
string  s = first(["a", "b"])     // T = string,  s : string
```

**Implémentation.** `T` est résolu en `TypeVariable` pendant le parse des types
(portée = chaîne des `FunctionBlock` englobants, `WordCompiler.findTypeParameter`).
À l'appel (`LeekFunctionCall.verifyVersions`) : inférence structurelle
(`inferTypeVariables` param formel ↔ arg effectif) → `substitute` dans le type de
retour, réutilisant la résolution par distance de cast existante. No-op pour les
versions non génériques (zéro impact existant). Une variable non liée s'efface
vers sa borne (`any`) ; le retour effacé `Object` est re-casté au site d'appel.

### 1.2 Signatures système génériques ✅

Les fonctions de la bibliothèque qui le justifient sont désormais typées
précisément au lieu de retourner `any` :

```leekscript
Array<integer> a = [3, 1, 4, 1, 5]
integer m = a.max()                       // -> integer, pas any
Array<integer> b = a.map(x -> x * 2)      // map<T,R> : Array<R>
```

**Implémentation.** Les `CallableVersion` portent des `TypeVariable`. Inférence
**contravariante** : une variable n'est inférée que depuis le *retour* d'un
callback, jamais ses paramètres (sinon le `any` d'un lambda non typé polluerait
`T`). Les params de callback de la stdlib restent `any` (LeekScript ne type pas
contextuellement les lambdas).

### 1.3 Classes génériques ✅

La déclaration, la portée des paramètres de type, l'effacement **et le typage précis
à l'instanciation** fonctionnent :

```leekscript
class Box<T> {
    T value
    constructor(T v) { value = v }
    T get() { return value }
}

var b = new Box(5)     // inféré Box<integer> depuis l'argument du constructeur
integer i = b.get()    // -> integer (plus `any`) ; assigner à un string warn en strict
```

**Implémentation.** Déclaration : interface partagée `TypeParameterScope` (implémentée
par `FunctionBlock` et `ClassDeclarationInstruction`) ; `T` se résout dans les types
des champs/méthodes/constructeur.

Instanciation précise : `ParameterizedClassType` (= `ClassType` + `Map<TypeVariable,
Type>` de liaisons). À `new Box(5)` (branche `VariableType.CLASS` de `LeekFunctionCall`),
on infère les liaisons depuis les **arguments du constructeur** avec le même
`inferTypeVariables` que les fonctions ; les variables non liées s'effacent vers `any`.
`member()`/`elementAccess()` substituent les liaisons, donc `b.value` (champ) comme
`b.get()` (méthode) se lisent précisément. Pas de syntaxe explicite `new Box<integer>(…)`.
Variance **invariante** (`Box<integer>` ≠ `Box<string>`), un `ClassType` brut reste
assignable des deux côtés (permissif par effacement). Codegen **inchangé** (mêmes noms
`u_<Class>`, classe Java non générique) ; seule subtilité : la méthode/le champ effacés
renvoient `Object` en Java, donc on insère un cast `(Wrapper)` au site d'accès quand le
type inféré est concret (sinon `ops((Object)…)` affecté à un primitif casse au javac).

### Variance

Démarrer **invariant** partout (sûr, = comportement actuel d'`ArrayType.accepts`).
Ajouter la covariance en position lecture seule plus tard.

## 2. Bibliothèque standard objet

Objectif : « plus de fonctions qui traînent seules ». La stdlib devient objet :
des **méthodes** sur les valeurs et des **namespaces** pour les fonctions
statiques/utilitaires.

Chaque fonction de `LeekFunctions` porte déjà un `standardClass` (`"Number"`,
`"String"`, `"Array"`, `"JSON"`…) et un flag `isStatic` — c'est la source qui
alimente les deux formes ci-dessous. Deux formes de codegen coexistent :
statique (`NumberClass.sqrt(ai, x)`) et instance (`((ArrayLeekValue) a).sort(ai)`).

### 2.1 Méthodes sur les valeurs ✅

`valeur.méthode(args)` sur les types natifs Array, Map, Set, String, Number :

```leekscript
var a = [3, 1, 2]
a.sort()                       // mutation en place
a.push(4)
var n = a.count()              // 4
var d = [1, 2, 3].map(x -> x * 2)   // [2, 4, 6]

var s = "Hello"
s.length()                     // 5
s.toUpper()                    // "HELLO"
s.substring(1, 3)              // "ell"

var x = -5
x.abs()                        // 5
(9.0).sqrt()                   // 3.0  (receveur typé/var, pas littéral)
```

**Implémentation.** `standardClassOf(Type)` / `methodFor(Type, name)` côté
compilo ; codegen branche sur `isStatic()` (instance `((ArrayLeekValue) x).m(ai)`
vs statique `StringClass.m(ai, recv, args)`). Pour un receveur de type statique
`any` (`var x = …`, très courant), résolution **runtime** dans
`AI.callObjectAccess` (gardée v≥5). Les noms sont propres : `LeekFunctions.javaName`
découple le nom leekscript du nom Java (`map` → `arrayMap`), `alias()` enregistre
un alias method-only. Marche sur receveur typé, `var` et littéral.

### 2.2 Suppression des formes libres Array/Map/Set/String ✅

En **v5**, les fonctions de collection ne sont plus appelables en forme libre :
**erreur dure** qui pointe vers la forme méthode.

```leekscript
// v5
var a = [3, 1, 2]
sort(a)        // ❌ erreur : utilise a.sort()
a.sort()       // ✅
push(a, 4)     // ❌ erreur : utilise a.push()
a.push(4)      // ✅
```

**Implémentation.** Une boucle abaisse `maxVersion=4` pour les ~100 fonctions
Array/Map/Set/String et pose un `replacement` = nom de méthode propre. v1–v4
inchangés. Les fonctions **math** de Number sont aussi retirées en v5 (voir §2.4) ;
les utilitaires bit/entier de Number, et Value/JSON/System/Color, restent libres.

### 2.3 Namespaces ✅

Les fonctions statiques/utilitaires sont regroupées dans des **namespaces**.
`Namespace.func(args)` se résout et se génère **exactement** comme l'ancienne
forme libre `func(args)`, juste qualifié et gardé v≥5.

```leekscript
// Mathématiques — résout aussi rand/randInt (pas de receveur de valeur)
Math.sqrt(16)          // 4.0
Math.abs(-5)           // 5
Math.pow(2, 10)        // 1024.0
Math.max(3, 7)         // 7
Math.rand()            // réel dans [0, 1)
Math.randInt(0, 10)

// JSON (noms propres : jsonEncode -> JSON.encode)
JSON.encode([1, 2, 3]) // "[1,2,3]"
JSON.decode("[1,2,3]") // [1, 2, 3]

// String (helpers statiques)
String.charAt("hello", 1)     // "e"
String.split("a,b,c", ",")    // ["a", "b", "c"]

// Array / Map / Set — la forme namespace reste valide même si la forme libre
// est retirée en v5
Array.sort(a)
Array.map([1, 2, 3], x -> x * 2)
Map.size(m)
Set.contains(s, 2)

// Number (équivalent de Math), System
Number.sqrt(9.0)       // 3.0
System.debug(x)
```

Namespaces exposés : **Math, Number, String, Array, Map, Set, JSON, System**.

**Implémentation.** Chaque namespace est une classe interne (comme `JSON`/`System`,
`Math` ajouté gardé v≥5) ; `LeekFunctions.namespaceFunction(ns, field)` mappe le
nom de namespace vers sa classe standard (`Math` → `Number`, les autres par
identité). Le codegen du callee système est factorisé (`writeSystemFunctionCallee`)
et **partagé** entre forme libre et forme namespace. Trois points :

1. La suppression `maxVersion=4` (§2.2) ne s'applique **pas** aux appels
   namespace : `sort(a)` est une erreur en v5, mais `Array.sort(a)` reste valide
   (garde `!is_namespace_function` dans `verifySystemFunction`).
2. Le codegen utilise `getJavaName()` (pas `getName()`) pour les fonctions
   aliasées (`JSON.encode` → `jsonEncode`, `Array.map` → `arrayMap`) ; identique
   sans alias, donc zéro impact sur les formes libres existantes.
3. `Color` n'est pas exposé : aucune classe interne `Color` n'est enregistrée.

### 2.4 Politique « plus de fonctions qui traînent »

| Catégorie | Forme libre en v5 | Forme canonique v5 |
|-----------|-------------------|--------------------|
| Collections (Array/Map/Set/String) | ❌ erreur dure | `a.sort()` ou `Array.sort(a)` |
| Mathématiques (sqrt, abs, cos, min, max, pow…) | ❌ erreur dure | `Math.sqrt(x)` |
| Bit/entier (binString, bitLength, hexString…) | tolérée | (reste libre, pas des maths) |
| JSON, System | tolérée | `JSON.encode(v)`, `System.debug(x)` |
| Fonctions métier (`getCell`…) | hors périmètre du cœur | traité côté générateur |

Les fonctions **métier** du générateur (injectées via `extraFunctions`) sont hors
périmètre du cœur leekscript ; leur regroupement objet sera traité séparément.

**Constantes de namespace ✅** : `Math.PI`, `Math.E`, `Math.Infinity` (accès de champ,
pendant v5 des constantes libres ; champs `final` non assignables). Comme pour les
fonctions, il faut les deux côtés : compile-time dans `MainLeekBlock` (typage, gardé
v≥5) ET runtime dans `AI` (`mathClass.addStaticField`, sinon le `getField(mathClass…)`
généré ne résout pas). `NaN` non exposé (non représentable en littéral Java). Les
constantes entières/réelles restent sur `Integer`/`Real` (`Integer.MAX_VALUE`…).

**Suppression des formes libres math ✅** : en v5, `sqrt(x)`/`abs(x)`/`cos(x)`/`min`/`max`/
`pow`/`floor`/`rand`… sont une **erreur dure** (REMOVED_FUNCTION_REPLACEMENT) pointant vers
`Math.sqrt(x)`. Même mécanique que les collections (§2.2) : une liste EXPLICITE de noms math
(pas tout `standardClass=Number`, qui contient aussi des utilitaires bit/entier `binString`/
`bitLength`/`hexString`/`isNaN`… qui RESTENT libres) passe `maxVersion=4` + `replacement="Math."+nom`.
La forme `Math.f(x)` reste valide (gardée `!is_namespace_function`). Migration : ~270 assertions
de test cappées à v4 (la forme libre reste testée v1-4 ; le v5 l'est via les ~20 tests `Math.*`).

## 3. Modules ❌ (planifié)

Remplacer le `include()` à fusion plate par de vrais modules (un fichier = un
module, symboles privés par défaut).

```leekscript
// utils.lk
export function clamp(x, lo, hi) { ... }
export class Vec { ... }
function helper() { ... }            // non exporté = privé au module

// main.lk
import { clamp, Vec } from "utils"
import * as Geo from "geometry"
```

**Implémentation prévue.** `ModuleScope` entre le scope global et le fichier,
tables de symboles **par module** au lieu de la fusion unique ; codegen à une
seule classe Java mais noms qualifiés par module (`module$utils$clamp`). Réutilise
le DAG `IncludeGraph` existant (cycles gérés par le double-pass). `include()`
reste pour v≤4 et comme échappatoire.

Découpage : 3a. parse `export`/`import … from` · 3b. `ModuleScope` + résolution
qualifiée + codegen renommé · 3c. `import * as Ns`.

## 5. Invariants de non-régression

- La suite `src/test/java/test/` reste **verte à chaque commit** (~20 200 tests).
- Toute règle stricte v5 est **inopérante** en v1–v4.
- Sur du code qui compilait avant, préférer la dégradation gracieuse (warning) à
  l'erreur dure (sauf breaking change v5 décidé et documenté, ex. §2.2).
