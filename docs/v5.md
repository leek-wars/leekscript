# LeekScript v5 — Spécification, roadmap et état d'avancement

> Document de référence du langage **LeekScript v5** (branche `v5`).
> Pour les détails d'implémentation interne (effacement, gates, choix de codegen),
> voir [v5-design.md](v5-design.md). Ce document décrit **le langage** (syntaxe,
> sémantique, exemples) et **l'avancement**.

LeekScript v5 fait évoluer le langage sur trois piliers — **génériques**,
**bibliothèque standard objet**, **modules** — sans casser la sémantique des
versions 1 à 4. Toute nouvelle sémantique est gardée derrière `version >= 5`.

- `LATEST_VERSION = 5` (les IA choisissent leur version via `@version: 5`).
- Le comportement v1–v4 est **gelé** : aucun changement observable en deçà de v5.
- Les bascules v5 passent par `leekscript/common/LanguageFeature.java`
  (`GENERICS(5)`, `OO_STDLIB(5)`), pas par des `>= 5` épars.

## 1. Génériques

Les génériques sont **purement compile-time** (effacement vers `any` à
l'exécution) : aucun changement du runtime, le moteur reste dynamique.

### 1.1 Fonctions utilisateur génériques ✅

Les paramètres de type se déclarent **après le nom** de la fonction (la syntaxe
`function<…>` est déjà réservée au type `Function<…>`).

```leekscript
function first<T>(Array<T> list) -> T {
    return list[0]
}

integer x = first([1, 2, 3])      // T = integer, x : integer
string  s = first(["a", "b"])     // T = string,  s : string
```

L'inférence est structurelle (`Array<T>` ↔ argument effectif), puis le type de
retour est substitué. Une variable non liée s'efface vers `any`. Zéro impact sur
les fonctions non génériques.

### 1.2 Signatures système génériques ✅

Les fonctions de la bibliothèque qui le justifient sont désormais typées
précisément au lieu de retourner `any` :

```leekscript
Array<integer> a = [3, 1, 4, 1, 5]
integer m = a.max()                       // -> integer, pas any
Array<integer> b = a.map(x -> x * 2)      // map<T,R> : Array<R>
```

Inférence **contravariante** : une variable n'est inférée que depuis le *retour*
d'un callback, jamais ses paramètres (sinon le `any` d'un lambda non typé
polluerait `T`).

### 1.3 Classes génériques ✅ (déclaration) / ⏳ (instanciation précise)

La déclaration, la portée des paramètres de type et l'effacement fonctionnent :

```leekscript
class Box<T> {
    T value
    constructor(T v) { value = v }
    T get() { return value }
}

var b = new Box(5)
var v = b.get()        // marche par effacement (T ≈ any à l'usage pour l'instant)
```

⏳ **Reste** : le typage précis à l'instanciation (`new Box(5)` infère
`Box<integer>` depuis les arguments du constructeur, `b.get()` rendrait alors
`integer`). Mécanique prévue : `ParameterizedClassType` (ClassType + bindings),
`member()` substitue les bindings. Pas de syntaxe explicite `new Box<integer>(…)` ;
cas ambigu/sans constructeur → `T` reste `any`.

## 2. Bibliothèque standard objet

Objectif : « plus de fonctions qui traînent seules ». La stdlib devient objet :
des **méthodes** sur les valeurs et des **namespaces** pour les fonctions
statiques/utilitaires.

### 2.1 Méthodes sur les valeurs ✅

`valeur.méthode(args)` sur les types natifs Array, Map, Set, String, Number :

```leekscript
var a = [3, 1, 2]
a.sort()                       // mutation en place
a.push(4)
var n = a.count()              // 4
var d = [1, 2, 3].map(x -> x * 2)   // [2, 4, 6]

var s = "Hello"
s.length()                     // 5
s.toUpper()                    // "HELLO"
s.substring(1, 3)              // "ell"

var x = -5
x.abs()                        // 5
(9.0).sqrt()                   // 3.0  (receveur typé/var, pas littéral)
```

Marche sur receveur typé (`Array<integer> a`), `var` (dispatch runtime) et
littéral. Les noms sont propres : `arrayMap` est exposé en `.map()`, etc.

### 2.2 Suppression des formes libres Array/Map/Set/String ✅

En **v5**, les fonctions de collection ne sont plus appelables en forme libre :
c'est une **erreur dure** qui pointe vers la forme méthode.

```leekscript
// v5
var a = [3, 1, 2]
sort(a)        // ❌ erreur : utilise a.sort()
a.sort()       // ✅
push(a, 4)     // ❌ erreur : utilise a.push()
a.push(4)      // ✅
```

v1–v4 inchangés (les formes libres restent valides). Number/Value/JSON/System/Color
restent libres en v5 (voir 2.4).

### 2.3 Namespaces ✅

Les fonctions statiques/utilitaires sont regroupées dans des **namespaces**.
`Namespace.func(args)` se résout et se génère exactement comme l'ancienne forme
libre `func(args)`, juste qualifié et gardé v≥5.

```leekscript
// Mathématiques — résout aussi rand/randInt (pas de receveur de valeur)
Math.sqrt(16)          // 4.0
Math.abs(-5)           // 5
Math.pow(2, 10)        // 1024.0
Math.max(3, 7)         // 7
Math.rand()            // réel dans [0, 1)
Math.randInt(0, 10)

// JSON (noms propres : jsonEncode -> JSON.encode)
JSON.encode([1, 2, 3]) // "[1,2,3]"
JSON.decode("[1,2,3]") // [1, 2, 3]

// String (helpers statiques)
String.charAt("hello", 1)     // "e"
String.split("a,b,c", ",")    // ["a", "b", "c"]

// Array / Map / Set — la forme namespace reste valide même si la forme libre
// est retirée en v5
Array.sort(a)
Array.map([1, 2, 3], x -> x * 2)
Map.size(m)
Set.contains(s, 2)

// Number (équivalent de Math), System
Number.sqrt(9.0)       // 3.0
System.debug(x)
```

Namespaces exposés : **Math, Number, String, Array, Map, Set, JSON, System**.
`Math` mappe vers les fonctions de classe standard `Number` ; les autres portent
le nom de leur classe standard.

> ⚠️ La suppression de la forme libre (2.2) ne s'applique **pas** au namespace :
> `sort(a)` est une erreur en v5, mais `Array.sort(a)` reste valide (la fonction
> existe toujours, seule la forme libre nue est retirée).

### 2.4 Politique « plus de fonctions qui traînent »

| Catégorie | Forme libre en v5 | Forme canonique v5 |
|-----------|-------------------|--------------------|
| Collections (Array/Map/Set/String) | ❌ erreur dure | `a.sort()` ou `Array.sort(a)` |
| Mathématiques (sqrt, abs, cos…) | ⚠️ dépréciée (⏳ warning à venir) | `Math.sqrt(x)` |
| JSON, System | tolérée | `JSON.encode(v)`, `System.debug(x)` |
| Fonctions métier (`getCell`…) | hors périmètre du cœur | traité côté générateur |

⏳ **Reste** : émettre le **warning de dépréciation** sur les formes libres math
en v5 (forme `sqrt(x)` → suggère `Math.sqrt(x)`), et exposer les **constantes de
namespace** (`Math.PI`, `Number.MAX_VALUE` — accès de champ, pas un appel).

## 3. Modules ❌ (planifié)

Remplacer le `include()` à fusion plate par de vrais modules (un fichier = un
module, symboles privés par défaut).

```leekscript
// utils.lk
export function clamp(x, lo, hi) { ... }
export class Vec { ... }
function helper() { ... }            // non exporté = privé au module

// main.lk
import { clamp, Vec } from "utils"
import * as Geo from "geometry"
```

Implémentation prévue : `ModuleScope` entre le scope global et le fichier, tables
de symboles par module, codegen à noms qualifiés (`module$utils$clamp`), réutilise
le DAG `IncludeGraph` existant. `include()` reste pour v≤4 et comme échappatoire.

## 4. Roadmap

| Phase | Contenu | État |
|-------|---------|------|
| **0** | Branche v5, `LATEST_VERSION=5`, `LanguageFeature` | ✅ |
| **1** | Génériques cœur : `TypeVariable`, `substitute`, fonctions génériques | ✅ |
| **2** | Classes génériques (déclaration + effacement) | ✅ (typage précis ⏳) |
| **3** | Stdlib objet : méthodes + namespaces + retrait formes libres collections | ✅ (warning math ⏳) |
| **4** | Signatures système génériques (`map`/`filter`/`reduce` typés) | ✅ |
| **5** | Modules : `import`/`export` | ❌ |
| **6** | Gains issus des issues : #42 type guards, #44 @tailrec, #43 perf inférence | ❌ |

Chaque phase = **compilable + testée + non régressive** sur la suite v1–v4.

---

## 5. Invariants de non-régression

- La suite `src/test/java/test/` reste **verte à chaque commit** (~20 200 tests).
- Toute règle stricte v5 est **inopérante** en v1–v4.
- Sur du code qui compilait avant, préférer la dégradation gracieuse (warning) à
  l'erreur dure (sauf breaking change v5 décidé et documenté, ex. retrait des
  formes libres de collection en 2.2).
